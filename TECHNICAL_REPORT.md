# Optimized Transformer Layer: Technical Report

## Summary

`lab.py` replaces the reference Transformer path with an inference-oriented
implementation that:

1. packs the three FP32 Q/K/V projections into one larger QKV GEMM;
2. calls PyTorch `scaled_dot_product_attention` (SDPA), allowing PyTorch to
   select the available CUDA backend for the exact operation;
3. runs a submission-owned Triton kernel that fuses residual addition, padding
   zeroing, and LayerNorm between attention/FFN sublayers, uses Triton's
   published per-row reduction/warp heuristic, and safely reuses internal
   residual buffers in-place;
4. preserves the reference operation order for FP16/BF16 and for causal+padding
   inputs, where the benchmark's very strict numerical gate makes a more
   aggressive fused route unsuitable; and
5. can be run with `torch.compile` to fuse surrounding pointwise work such as
   residual operations and epilogues.

The source paper behind the attention choice is
[FlashAttention](https://arxiv.org/abs/2205.14135): it computes exact attention
without materializing the full score/probability matrices, reducing high
bandwidth memory traffic. PyTorch's
[SDPA tutorial](https://docs.pytorch.org/tutorials/intermediate/scaled_dot_product_attention_tutorial.html)
documents the corresponding fused PyTorch API, and its
[Accelerated PyTorch 2 post](https://pytorch.org/blog/accelerated-pytorch-2/)
describes the automatic fused-kernel selection and compiler integration. The
follow-up [FlashAttention-2 paper](https://arxiv.org/abs/2307.08691) identifies
sequence-length parallelism, reduced non-matmul work, and warp work partitioning
as the remaining attention bottlenecks; those are handled here by PyTorch's
vendor SDPA backend rather than by an unvalidated replacement kernel. The
custom residual/LayerNorm kernel follows the reduction structure in Triton's
[LayerNorm tutorial](https://github.com/triton-lang/triton/blob/main/python/tutorials/05-layer-norm.py)
and is exposed to the compiler with PyTorch's documented
[`triton_op` integration](https://docs.pytorch.org/tutorials/recipes/torch_compile_user_defined_triton_kernel_tutorial.html).
The launch uses Triton's documented `min(max(BLOCK_SIZE // 256, 1), 8)` warp
rule rather than an unverified machine-specific constant.

For completeness, [`tests/flash_attention_report.py`](tests/flash_attention_report.py)
contains a submission-owned tiled online-softmax kernel implementing the
FlashAttention recurrence directly. Its numerical output passes the isolated
workshop tolerance, but CUDA-event measurements show PyTorch SDPA's mature
vendor kernel is faster on the tested RTX 4060 shapes. The active path therefore
uses SDPA; the custom kernel is not silently substituted when it regresses.

### Backend verification

On the measured RTX 4060 run, a CUDA profiler trace of the same FP32 SDPA
shape recorded `fmha_cutlassF_f32_aligned_64x64_rf_sm80` (one fused attention
kernel), confirming that this path did not fall back to separate score,
softmax, and value-matmul kernels. The benchmark's timing itself still uses
CUDA events, not profiler overhead.

Per-operation CUDA-event measurements are generated by
[`tests/operation_profile_report.py`](tests/operation_profile_report.py) and summarized in
[`OPERATION_PROFILE_REPORT.md`](OPERATION_PROFILE_REPORT.md). Across the tested
medium and wide shapes, FFN GEMMs account for roughly 50–70% of isolated
operation time; QKV packing is the largest repeatable reduction, while SDPA is
most beneficial for small/batched or long-sequence shapes. The fused residual
LayerNorm is retained only when the end-to-end path amortizes its launch cost.

The factorial technique sweep uses paired, alternating baseline/variant CUDA
event measurements. Exact duplicate configurations across its axes (for
example `B8 S128`, `D512 H8`, `L6`, and `F2048`) are measured once and copied to
the alias rows. This matters on a laptop GPU: a long sweep can change clocks
and temperature, so a baseline measured once at the beginning can make a later
variant appear almost 2× slower even though the equations and tensors are
identical. The sweep report's speedup is therefore the within-row ratio; its
absolute milliseconds should not be compared with a separate `lab.py` process
run at a different power state.

### Accuracy audit and `tl` math experiment

The active path has no explicit `libdevice` import: its LayerNorm uses Triton's
`tl.rsqrt`, and the attention candidate uses Triton `tl` operations as well.
I also tested an all-`tl` software reciprocal-square-root candidate (integer
exponent seed plus two Newton steps). Across FP32 default, small, long,
causal, padded, wide-hidden, FP16, and BF16 cases, the active implementation
and the candidate both passed the workshop gate (`abs_error <= 0.001 OR
relative_error <= 1%`; zero failed elements). The candidate's isolated
LayerNorm timing was about 0.14 ms versus 0.035 ms for `tl.rsqrt` on the
default row, so it is retained as an experimental function but not selected
for the submission path. This avoids trading a measured slowdown for a
nominally different math primitive.

The old `B4 S64 / 10011` row (`4.7555 ms / 2.4264 ms = 1.960×`) was audited
with the same weights, input seed, and implementation using five alternating
rounds of 80 events: independent runs measured `1.230×`, `1.092×`, and
`1.097×`. Therefore `1.960×` is not a reproducible improvement; it came from
the short, drifting baseline measurement in the historical screening sweep.

## Correctness and performance results

All results use CUDA events, fixed input data, and the benchmark's default
criterion: `abs_error <= 0.001 OR relative_error <= 1%`. Timing is median
latency; the optimized row uses `--compile-user --compile-mode reduce-overhead`
for FP32. Compilation is warmed up before timing, so these are steady-state
inference numbers rather than first-call latency, and the baseline is eager
while the optimized submission is compiled.

| Shape / conditions | Accuracy | Baseline | Optimized | Speedup |
| --- | ---: | ---: | ---: | ---: |
| B=8, S=128, D=512, H=8, FFN=2048, L=6, FP32 + compiled user | 0 failures / 1,048,576 | 6.1460 ms | 5.0473 ms | 1.218x |
| B=2, S=64, D=256, H=4, FFN=1024, L=2, FP32 eager | 0 failures / 65,536 | 0.5627 ms | 0.4220 ms | 1.334x |
| B=8, S=128, D=512, causal + 25% padding | 0 failures / 1,048,576 | 5.6038 ms | 5.5731 ms | 1.006x |
| B=2, S=128, D=512, causal, L=3 | 0 failures / 262,144 | 1.2677 ms | 1.2646 ms | 1.002x |
| B=2, S=64, D=256, H=4, FP16 eager | 0 failures / 65,536 | 0.5151 ms | 0.4812 ms | 1.070x |

The default configuration was repeated with the same command and stayed above
the previous 1.133× result (1.218× in the latest run; 1.215× in an earlier
repeat). This is steady-state timing only, so clocks and background GPU load
can move the median between runs.

## Reproduction

From `Documents`:

```bash
.venv/bin/python tiktok/lab.py \
  --device cuda --dtype float32 \
  --compile-user --compile-mode reduce-overhead
```

For a causal padded validation:

```bash
.venv/bin/python tiktok/lab.py \
  --device cuda --dtype float32 --causal --padding-ratio 0.25 \
  --compile-user --compile-mode reduce-overhead
```

FP16 and BF16 automatically use a compiler-disabled reference-order fallback,
so they still pass the tight numerical comparison exactly even when the command
contains `--compile-user`.

## Limitations and next steps

The custom Triton residual/LayerNorm kernel is currently an FP32 inference path;
FP16/BF16 use the strict fallback because small per-layer normalization
differences can accumulate beyond the benchmark threshold. Causal+padding also
uses the strict path to preserve the reference mask order. Attention itself uses
PyTorch's optimized CUDA SDPA rather than duplicating the mature vendor kernel.
The direct Triton FlashAttention candidate is available in
`transformer_kernels.py` and benchmarked in `FLASH_ATTENTION_REPORT.md`; it is
retained for reproducibility and future autotuning, not enabled blindly.
The LayerNorm dispatch is shape-specialized at both ends. Below 131,072
activation elements, native residual+LayerNorm avoids the custom launch
overhead. The custom one-program-per-row kernel remains enabled through 65,536
rows, the largest verified appendix grid. At 1,280,000 rows, repeated launches
caused a driver failure, so the B=10,000 stress case uses native LayerNorm while
retaining memory-efficient SDPA. Compiler compilation time is excluded from
steady-state timing and should be amortized in deployment.

The technique-by-shape factorial experiment is in
`TECHNIQUE_SHAPE_REPORT.md`. It measures all 32 combinations of QKV, SDPA,
Triton LN, in-place reuse, and shape-specialized LayerNorm across the 14
appendix shapes for 448 rows. An explicit-attention baseline is allowed to OOM;
the runner then independently attempts each memory-efficient SDPA combination
at full size and reports its latency without inventing a speedup denominator.
Correctness for such a row is checked against the unchanged baseline at
batch=1, which is valid because examples do not interact across the batch.
Only a shape whose input tensor itself cannot fit is rejected before execution.
`technique_shape_results.csv` and `technique_shape.png` contain the raw data and
heat map.
